description: GitHub PR の競合を解消する。`/resolve-conflicts` に PR 番号または PR URL だけが渡されたときに使う。競合解消以外の修正、レビュー対応、PR 作成には使わない。
---

GitHub PR の競合だけを解消し、PR のブランチへプッシュします。

## 入力

入力は次のどちらか1つです。

- PR 番号（例: `123`）
- PR URL（例: `https://github.com/owner/repo/pull/123`）

入力がない、PR を特定できない、または複数の値が渡された場合は、作業せず PR 番号か URL を1つだけ求めます。

## 進め方

1. `gh pr view {入力}` で PR を取得し、番号、URL、ベースブランチ、ヘッドブランチ、リポジトリ、`mergeable`、Draft かどうか（`isDraft`）を確認する。`mergeable` が `UNKNOWN` の場合は再取得する
2. URL のリポジトリが現在のリポジトリと異なる場合は、作業せずその旨を伝える
3. `mergeable` が `MERGEABLE` の場合は、コミットもプッシュも行わず、競合がないと報告する
4. `git status --short` で作業ツリーが空であることを確認する。変更がある場合は、上書きや退避をせず作業を止める
5. `gh pr checkout {入力}` で PR のヘッドブランチをチェックアウトする
6. ベースリポジトリのベースブランチを `git fetch` し、ヘッドブランチへ `--no-ff --no-commit` でマージする
7. 競合したファイルをすべて調べ、どれも解消のしかたを決められることを確かめる。決められない競合があれば、コミットせずに `git merge --abort` する
8. [コミットの分け方](#コミットの分け方)に従い、競合マーカーを残したままマージコミットを作り、そのあと競合を1か所ずつ解消してコミットする
9. 競合マーカーが残っていないこと、未解決ファイルがないこと、競合解消以外の差分がないことを確認する
10. 変更箇所に関係するテストや静的解析を実行する。コミット時のフックを飛ばしたので、フックで行う整形や静的解析も手で実行する
11. PR のヘッドブランチへ通常のプッシュを行う
12. PR が Draft でなければ、[概要欄への記録](#概要欄への記録)に従い、PR の概要欄に競合と解消のしかたを残す
13. PR URL、解消した競合、実行した確認、コミット SHA を報告する

## 競合の解消方針

- PR 側の変更目的と、ベースブランチ側の最新仕様を両方確認して判断する
- 片方を機械的に採用しない。`--ours` や `--theirs` は、ファイル全体を採用してよいと確認できた場合だけ使う
- 競合していないコードを整形し直したり、リファクタリングしたりしない
- lockfile の競合は、対応する定義ファイルを先に解消してから、リポジトリで使っているパッケージ管理ツールで再生成する
- 生成物の競合は、元ファイルを先に解消してから、既存の生成手順で再生成する
- 競合解消後に新しい不整合が見つかった場合は、今回のマージで生じたものだけ直す

## コミットの分け方

競合は、原則1か所1コミットで解消します。各コミットの差分が「競合マーカー込み → 解消後」になり、レビュアーが1か所ずつ確かめられるようにするためです。

1. 競合マーカーを残したまま、競合したファイルを `git add` し、マージコミットを作る
   - 例: `chore: {ベースブランチ} を取り込む（競合は後のコミットで解消する）`
2. 競合を1か所解消するごとに、そのファイルだけを `git add` してコミットする
   - 例: `fix: {ファイル名}の競合を解消する`。本文に、どう解消したかを書く
   - 同じ修正になる競合は、ファイルをまたいでも1コミットにまとめてよい（両側の import を残すだけ、など）
3. 競合マーカーが残っている間は、コミット時のフック（整形や lint）が失敗するので `--no-verify` を付ける。すべて解消したら、フックで行う整形や静的解析を手で実行し、差分があれば別のコミットにする
4. 競合しなかったが、マージに合わせて直したところ（型や API の変更に合わせたテストなど）は、競合を解消するコミットとは別にコミットする

- 画像などのバイナリには競合マーカーを残せない。マージコミットではヘッドブランチ側を入れ、作り直したものを別のコミットにする

- コミットは `commit` スキルに従う
- マージコミットから最後の競合解消までの途中のコミットは、ビルドやテストが通らなくてよい

## 概要欄への記録

競合を解消したら、Draft でない PR では必ず概要欄に記録します。レビュアーが競合ごとに、何がぶつかって、どう解消したかをコードで確かめられるようにするためです。

Draft の PR では記録しません。まだレビューする段階ではないためです。

### 構成

`## やったこと` の節のすぐ後ろに、次の節を足します。PR 自体がブランチの取り込みだけの場合は、`## やったこと` をこの節に置き換えます。

````markdown
## やったこと（コンフリクト解消）

### コンフリクト一覧

<details>
<summary>{何の競合か}（{競合の数} か所）</summary>

- ぶつかったところ: {ベースブランチ} は〜した。{ヘッドブランチ} は〜していた
- 解消のしかた: 〜した

解消したコミット: {コミットのフル SHA}

**1 か所目**: `{ファイルパス}`

競合マーカー込み（L{行番号}〜）

```{言語}
{競合マーカー込みのコード}
```

解消後（L{行番号}〜）

```{言語}
{解消後のコード}
```

</details>

### 競合はしなかったが、合わせて直したところ

- 〜した。〜のため: {コミットのフル SHA}
````

### 書き方

- 折り畳みは、同じ変更（競合を解消した1コミット）ごとに作る。ファイルごとにしない。同じ解消のしかたの競合を、まとめて確かめられるようにするため
- 折り畳みは、競合を解消したコミットの順に並べる
- 折り畳みの見出しは、何の競合かと競合の数だけにする（例: `uploads の Procedure（2 か所）`）。コミットの件名から「の競合を解消する」を除いたものでよい。説明は折り畳みの中に書く
- 「ぶつかったところ」と「解消のしかた」は、折り畳みごとに書き分ける。まとめて表にしない
- 各か所の先頭に、ファイルパスを書く。競合が1か所だけの折り畳みは「1 か所目」を書かず、ファイルパスだけにする
- 「解消したコミット」には、その折り畳みの競合を解消したコミットのフル SHA（40文字）を書く。GitHub がコミットへのリンクにするよう、両側に半角スペースを入れる
- コードは、競合ブロックと前後3行にする。間が7行以内の競合ブロックは1つにまとめる
- コードブロックには、ファイルの言語を指定する。GitHub にはコンフリクトマーカー用の言語がないため、マーカーには色が付かない
- 競合マーカーのラベルはブランチ名にする（`<<<<<<< {ヘッドブランチ}`、`>>>>>>> {ベースブランチ}`）。コミット SHA や `HEAD` のままにしない
- 解消後のコードは、最後の競合を解消したあとのコードの同じ場所を載せる。競合ブロックの前後の行を手がかりに探す。空行や `import` のようによく出てくる行だけで探すと、別の場所に当たるので、取り出した結果を目で確かめる
- 画像などのバイナリは1つの折り畳みにまとめ、ファイルの一覧と解消のしかたを書く
- 競合しなかったが、マージに合わせて直したところ（型や API の変更に合わせたテストなど）は「競合はしなかったが、合わせて直したところ」に書く。各項目の末尾に、直したコミットのフル SHA を書く。なければ節ごと省く
- 次のことは書かない。見れば分かるため
  - 競合マーカーの読み方
  - 「取り込んだ」「両方の変更を残した」のような要約
- 2回目以降の競合解消では、既存の記録を消さない。新しい一覧を後ろに足し、見出しにマージコミットの短縮 SHA を付ける（例: `### コンフリクト一覧（a1b2c3d）`）

### 競合マーカー込みのコードの取り出し方

競合マーカーはマージコミットに残っているので、そこから取り出します。

```bash
# 競合マーカー込みのコード
git show {マージコミット}:{ファイルパス}
# 解消後のコード
git show {最後の競合を解消したコミット}:{ファイルパス}
```

- 競合したファイルの一覧は、マージコミットで `<<<<<<< ` を含むファイルを `git grep` で探す
- ラベルは `HEAD` や `origin/{ベースブランチ}` になるので、ブランチ名に置き換える

### 概要欄の更新

- 概要欄の文字数の上限は 65,536 文字。超える場合は、収まらないファイルの分を PR コメント（見出し `### コンフリクト一覧（続き）`）に分け、概要欄からコメントの URL へリンクする
- 更新したら、GitHub 上の概要欄を読み直し、反映されたことを確かめてから報告する。`gh pr edit` が成功しても、反映されていないことがある

## やらないこと

- `rebase`、`reset`、force push で履歴を書き換えない
- PR のタイトル、ラベル、レビューコメントを変更しない。本文は、競合の記録を足すことだけ行う
- 競合解消と無関係な修正を加えない
- 判断材料が足りない競合を推測で解消しない。その場合はマージコミットを作る前に `git merge --abort` でマージ前へ戻し、未解決箇所と必要な判断を報告する
- 競合マーカーを残したマージコミットだけをプッシュしない。すべての競合を解消してからプッシュする
- テスト失敗を隠したり、既存のテストを削除したりしない
