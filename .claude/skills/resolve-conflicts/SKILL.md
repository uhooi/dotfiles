description: GitHub PR の競合を解消する。`/resolve-conflicts` に PR 番号または PR URL だけが渡されたときに使う。競合解消以外の修正、レビュー対応、PR 作成には使わない。
---

GitHub PR の競合だけを解消し、PR のブランチへプッシュします。

## 入力

入力は次のどちらか1つです。

- PR 番号（例: `123`）
- PR URL（例: `https://github.com/owner/repo/pull/123`）

入力がない、PR を特定できない、または複数の値が渡された場合は、作業せず PR 番号か URL を1つだけ求めます。

## 進め方

1. `gh pr view {入力}` で PR を取得し、番号、URL、ベースブランチ、ヘッドブランチ、リポジトリ、`mergeable` を確認する。`mergeable` が `UNKNOWN` の場合は再取得する
2. URL のリポジトリが現在のリポジトリと異なる場合は、作業せずその旨を伝える
3. `mergeable` が `MERGEABLE` の場合は、コミットもプッシュも行わず、競合がないと報告する
4. `git status --short` で作業ツリーが空であることを確認する。変更がある場合は、上書きや退避をせず作業を止める
5. `gh pr checkout {入力}` で PR のヘッドブランチをチェックアウトする
6. ベースリポジトリのベースブランチを `git fetch` し、ヘッドブランチへ `--no-ff --no-commit` でマージする
7. 競合したファイルだけを調べ、両ブランチの意図を保つ最小限の変更で解消する
8. 競合マーカーが残っていないこと、未解決ファイルがないこと、競合解消以外の差分がないことを確認する
9. 変更箇所に関係するテストや静的解析を実行する
10. `commit` スキルに従ってマージコミットを作成し、PR のヘッドブランチへ通常のプッシュを行う
11. PR URL、解消した競合、実行した確認、コミット SHA を報告する

## 競合の解消方針

- PR 側の変更目的と、ベースブランチ側の最新仕様を両方確認して判断する
- 片方を機械的に採用しない。`--ours` や `--theirs` は、ファイル全体を採用してよいと確認できた場合だけ使う
- 競合していないコードを整形し直したり、リファクタリングしたりしない
- lockfile の競合は、対応する定義ファイルを先に解消してから、リポジトリで使っているパッケージ管理ツールで再生成する
- 生成物の競合は、元ファイルを先に解消してから、既存の生成手順で再生成する
- 競合解消後に新しい不整合が見つかった場合は、今回のマージで生じたものだけ直す

## やらないこと

- `rebase`、`reset`、force push で履歴を書き換えない
- PR のタイトル、本文、ラベル、レビューコメントを変更しない
- 競合解消と無関係な修正を加えない
- 判断材料が足りない競合を推測で解消しない。その場合は `git merge --abort` でマージ前へ戻し、未解決箇所と必要な判断を報告する
- テスト失敗を隠したり、既存のテストを削除したりしない
